# Architecture

A crowdsourced airport security wait time app. React + Vite on the front,
Express on the back, Postgres via Drizzle, deployed as a static bundle plus one
serverless function on Vercel.

## The accuracy model

This is the part worth understanding. Everything else is plumbing.

### Observations

An observation is one data point about how long a line was, at a moment:

- a **report** somebody typed, or
- an **agreement** — someone tapping "still about right" on an existing report,
  which is recorded as a fresh observation of that same wait at the moment it
  was tapped. Agreement carries less trust than a typed report (0.6), because
  agreeing is easier than judging.

A **disagreement** doesn't create an observation. It halves what the report it
landed on counts for, floored so a single grudge can't erase a report.

### From observations to a number

`server/wait-model.ts` — pure functions, an explicit `now`, no randomness.

1. **Pick a window.** 90 minutes if at least two observations fall inside it,
   otherwise widen to 180, then 360. Nothing older than 6 hours is ever loaded.
2. **Decay by age.** Weight is `0.5 ^ (ageMinutes / 30)` — influence halves
   every half hour.
3. **Take the weighted median**, with each observation positioned at the
   midpoint of the weight it occupies and the answer interpolated between those
   positions. A mean would let one bad entry move the number by 40 minutes.
4. **Grade confidence** from total effective weight, the age of the freshest
   observation, and the interquartile spread relative to the median.
5. **Blend toward the baseline** when effective weight is below 3, in
   proportion to how little the crowd has said. At or above 3 the baseline
   drops out entirely.
6. **Emit a range**, widened by confidence and never tighter than ±3 minutes.

Everything is computed per line type. Nothing is ever pooled across Standard,
PreCheck and CLEAR.

### Baselines

`airport_baselines` holds an expected wait for every
(airport, line type, local day, local hour) — 16,128 rows, generated by
`migrations/setup.sql` from three curves: an hour-of-day shape with a heavy
pre-dawn bank and a midday trough, a day-of-week shape with Monday running ~36%
above Wednesday, and per-line shares.

The table is authoritative. Application code only reads it, so replacing
modelled numbers with measured ones is a data change — update `wait_minutes`
and set `source = 'observed'`, no deploy. `server/baselines.ts` caches the grid
in memory for 10 minutes and interpolates between adjacent hours so the number
drifts smoothly rather than stepping at :00.

There is a flat per-tier fallback in code for the case where the table hasn't
been seeded. It logs a warning. It is a safety net, not a second model.

### Forecasting and the departure planner

`server/forecast.ts` — also pure, also an explicit `now`.

A current number can't answer "when should I leave". Somebody checking at 2pm
for a 6pm flight is asking about the evening peak. So:

1. Measure **today's deviation** — the current community estimate divided by
   the baseline for right now, clamped to [0.4, 2.5]. When we only have the
   baseline, this is exactly 1: dividing an estimate by the baseline it came
   from tells us nothing, and treating it as signal would let the model
   amplify its own guess.
2. **Decay that deviation** toward 1 with a two-hour half-life. A line running
   double an hour from now says a lot about the next 30 minutes and very
   little about tonight.
3. Multiply it into the baseline for the *target* hour, so the forecast still
   follows the day's shape.
4. Widen the range and cap confidence by horizon.

`planDeparture` then works backwards from the flight: boarding lead, gate
transit (per airport — ATL's plane train is not a rounding error), the security
forecast, bag drop, and a margin the traveller picks.

Two decisions worth knowing:

- It plans against the **top** of the forecast range, not the midpoint. Ten
  minutes early costs nothing; ten minutes late costs the flight. That
  asymmetry is why the model carries a range at all.
- The forecast depends on when they reach security, which depends on the
  forecast. It settles in two passes.

Bag-drop cutoffs are returned as information rather than as a constraint that
binds: boarding lead plus bag-drop time already exceeds every cutoff we model.
The clamp stays as a guard so that remains an invariant rather than a
coincidence, and a test asserts it across every combination of options.

### Local time

`server/local-time.ts` resolves an instant into an airport's own wall clock via
its IANA zone. Reading the server's clock instead would shift the morning rush
by four hours at JFK and ten at HNL — the server is UTC on Vercel.

### Free-text grouping

People type whatever the signage above them says. `server/normalize.ts` reduces
a label to a stable grouping key ("North", "north", "N", "North Checkpoint" all
collapse) while the raw text is stored and the most-used spelling is what gets
displayed. The report form suggests names other travelers have already used at
that airport, so the vocabulary converges on the real signage without anyone
having to hand-curate a checkpoint list for 32 airports.

## Integrity

There are no accounts. Instead:

- A random per-install **device token** in localStorage, sent as
  `X-Tarmac-Device`. Reports without one are rejected — otherwise the rate
  limit is optional for anyone who omits the header.
- **Rate limits**: one report per device per airport per 20 minutes, and 8 per
  device per hour across all airports.
- **Salted IP hashes** (`REPORT_HASH_SALT`), so abuse can be grouped and
  cleaned up without ever storing an address.
- **Plausibility check** against the baseline. Implausible values are stored
  with `status = 'flagged'` and excluded from every aggregate — retained rather
  than dropped, because a filter that silently deletes data can't be debugged.
- One vote per device per report, enforced by a unique index. You can't confirm
  your own report.

## Data flow

```
client ──GET /api/airports?line=…──▶ routes ──▶ storage
                                                  │
                                    ┌─────────────┴─────────────┐
                                    ▼                           ▼
                          recent reports +            baseline lookup
                          confirmations               (cached grid,
                          (last 6h, indexed)           local hour)
                                    │                           │
                                    └─────────┬─────────────────┘
                                              ▼
                                        wait-model
                                    (decay → median →
                                     confidence → blend)
                                              │
                                              ▼
                                    { waitMinutes, low, high,
                                      confidence, dataSource,
                                      sampleCount, newestObservationAt }
```

The list endpoint loads every airport's recent reports in one query and groups
in memory, so the list and the detail page run identical maths and cannot
disagree.

## API

| Endpoint | Notes |
|---|---|
| `GET /api/health` | Self-diagnosing. Never returns raw driver errors. |
| `GET /api/airports?line=` | All airports; `wait` for the requested line, `byLineType` for all three |
| `GET /api/airports/:code?line=` | One airport, same shape |
| `GET /api/airports/:code/labels` | Terminal/checkpoint names in use here |
| `GET /api/airports/:code/forecast?line=&hours=` | Hourly forecast, local hours |
| `GET /api/airports/:code/plan?departureAt=&…` | Leave-by time. `no-store` — depends on `now` |
| `GET /api/reports/:code` | Last 6 hours, with confirmation tallies |
| `GET /api/checkpoints/:code` | Grouped by terminal, checkpoint and line |
| `POST /api/reports` | Requires `X-Tarmac-Device`. 429 on cooldown. |
| `POST /api/reports/:id/confirm` | `{ agrees: boolean }` |

Read endpoints set a short `s-maxage` so polling clients hit the CDN rather
than Postgres. Every timestamp crossing the wire is ISO-8601 UTC.

## Conventions

- **Timestamps** are `timestamptz` in the database and ISO-8601 with an offset
  on the wire. Never serialize a timestamp with a bare `::text` cast.
- **Server modules** import each other with explicit `.js` extensions so the
  bundled output resolves at runtime. `vitest.config.ts` maps them back to the
  TypeScript sources for tests.
- **`migrations/setup.sql` is the schema's single definition.** `npm run db:seed`
  applies that same file. `npm run db:push` (drizzle-kit) is a convenience for
  local development against `shared/schema.ts`.
- **The model stays pure.** Anything in `wait-model.ts`, `local-time.ts` or
  `normalize.ts` takes its inputs explicitly — including the current time — so
  it can be tested. That is what makes the accuracy claims checkable.
